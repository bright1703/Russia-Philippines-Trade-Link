# Trade Agent Intelligence

Небольшой автоматизированный аналитический отдел торгового представителя
Приморского края, который работает на Филиппинах.

Система собирает информацию по ДВУМ направлениям торговли, отбрасывает шум,
связывает события с компаниями каталога, проверяет собственные выводы и
показывает человеку короткий обзор — два раза в неделю.

| Направление | Что отслеживается |
|---|---|
| Приморье → Филиппины | филиппинский спрос и импорт, конкурирующие поставщики, условия доступа, закупки, логистика |
| Филиппины → РФ | филиппинский экспорт и условия ввоза в РФ по тем же товарным группам |

Упоминание России в каждой новости не требуется: изменение филиппинского
импорта рыбы из третьей страны влияет на спрос и конкуренцию для Приморья.
Но причинная связь должна быть объяснима, а событие третьего рынка без связи
с Филиппинами, РФ или маршрутом между ними не берётся вовсе.

**Решение всегда принимает человек.** Система ничего не отправляет третьим
лицам, не подаёт заявки и не регистрирует компании.

## Три правила, на которых всё держится

1. **Доказательство — только из материала.** Товар, код и название компании
   засчитываются, если они есть в самом тексте новости. Поля, которые система
   заполнила сама из профиля компании, уликой не являются: иначе связь
   подтверждает сама себя.
2. **Отрасль и тип события — разные вещи.** Рыба, лес, косметика — отрасли.
   Пошлина, тендер, логистика, изменение спроса — типы событий. Их нельзя
   складывать в одно поле.
3. **Состав выпуска считается один раз.** Карточки, счётчики, список компаний
   и посты в Telegram строятся из одного сохранённого набора `issue_items`,
   поэтому шапка не может противоречить содержимому.

## Конвейер

```
источники → сбор → нормализация → Scout → Analyst → Reviewer → база → выпуск → Telegram
```

Этапы независимы. Сбой одного не теряет данные остальных: сырьё сохраняется
до обработки, и если модель недоступна, материал остаётся в очереди.

Сбор идёт не «за последние сутки», а от последней успешной позиции каждого
источника с небольшим перекрытием. После простоя сервера пропущенный интервал
догружается, даже если он длиннее недели. Если источник упёрся в технический
лимит, остаток сохраняется в курсоре, а период помечается как покрытый
не полностью — делать вид, что всё обработано, нельзя.

## Быстрый старт

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -c constraints.txt      # production
# для разработки и тестов:
# pip install -r requirements-dev.txt -c constraints.txt
cp .env.example .env          # заполнить DEEPSEEK_API_KEY и токен бота

python -m trade_agent.fetch     # собрать сырьё от последней позиции источников
python -m trade_agent.process   # Scout → Analyst → Reviewer → Radar
python -m trade_agent.digest    # собрать выпуск
python -m trade_agent.bot       # команды /status, /latest, /companies
python -m trade_agent.notify    # доставить последний собранный выпуск
python -m trade_agent.run_pipeline             # полный прогон вручную
python -m trade_agent.run_pipeline --scheduled # плановый прогон по таймеру

# отчёт проверки классификации каталога (базу не меняет)
python -m trade_agent.companies.audit --out digest/catalog-audit.md

# образец выпуска на воспроизводимом наборе материалов
python tools/sample_issue.py --days 4
```

## Расписание

Два автоматических прогона в неделю: понедельник и четверг, 08:00 по Маниле.
Время сервера не меняется — зона указана только в таймере проекта.

`run_pipeline --scheduled` сам считает, сколько автоматических циклов уже было
с начала календарной недели по Маниле, и третий не начинает; догоняющий старт
после простоя тоже считается циклом. Одновременные прогоны исключены файловой
блокировкой. Чтение сохранённых данных ботом сбор и рассылку не запускает.

## Модели

В рабочем режиме используется официальный DeepSeek API через Anthropic-
совместимый интерфейс. Scout работает на `deepseek-v4-flash` без глубокого
рассуждения и быстро отбрасывает шум. Analyst и Reviewer работают на
`deepseek-v4-pro` с включённым рассуждением. Ответы ограничены отдельными
лимитами агентов: Scout — 600 токенов, Analyst — 2600, Reviewer — 1800.

Для переключения провайдера задаются `LLM_PROVIDER`, ключ соответствующего
провайдера и модели. Ключи не логируются и не отправляются в промпт.

Проверка без сети и без ключей:

```bash
TRADE_AGENT_FIXTURES=tests/fixtures python -m trade_agent.fetch --days 3650
python -m trade_agent.process --mock-llm      # ответы синтетические, это не анализ
python -m trade_agent.digest --days 3650
```

Тесты:

```bash
python -m pytest -q
```

## Структура

```
trade-agent/
  trade_agent/            Python-пакет (импортируемый, отсюда -m команды)
    config.py             настройки и .env
    models.py             сущности конвейера
    db.py                 SQLite: схема, атомарность, идемпотентность
    fetch.py              этап 1 — сбор с позиций источников
    process.py            этап 2 — агенты
    digest.py             этап 3 — сборка выпуска из issue_items
    events.py             устойчивый идентификатор события, дедупликация
    timeutil.py           UTC в хранении, Манила в показе
    locking.py            запрет одновременных прогонов
    alerts.py             обязательные триггеры с доказательствами
    bot.py                Telegram-бот доставки
    sources/              адаптеры источников (telegram, tenders, web)
    agents/               Scout, Analyst, Reviewer, таксономия, evidence
    llm/                  провайдеро-независимый клиент LLM
    radar/                Opportunity Radar
    companies/            чтение профилей и импорт каталога
    utils/                хэши, повторы, логирование, HTTP
  tenders/                существующий тендерный модуль (работает и отдельно)
  telegram/               необязательные экспорты и локальные credentials
  brain/                  человекочитаемая база знаний (Markdown)
  digest/                 latest.md, архив выпусков и образцы до/после
  tools/                  вспомогательные скрипты (образец выпуска)
  deploy/                 systemd unit-файлы и пример crontab
  tests/                  тесты системы (тесты tenders — в tenders/tests)
  data/                   SQLite (в Git не попадает)
  logs/                   логи (в Git не попадают)
  sources.yml             конфигурация источников
  .env.example            шаблон секретов
```

О том, почему пакет называется `trade_agent`, а каталог — `trade-agent`,
см. ARCHITECTURE.md, раздел «Именование модулей».

Для прямого read-only сбора используются `TELEGRAM_API_ID`,
`TELEGRAM_API_HASH` и уже авторизованная `TELEGRAM_SESSION_STRING` или
`TELEGRAM_SESSION`. Каталог `telegram/` нужен только для старого экспортного
режима.

## Что проверено, а что нет

| Проверено локально на фикстурах и моках | НЕ проверялось |
|---|---|
| сбор из `tenders` и Telegram-выгрузок | реальный DeepSeek API |
| нормализация, дедупликация, БД | реальный Telegram Bot и Telethon |
| Scout / Analyst / Reviewer на мок-ответах | живая вёрстка сайтов ведомств |
| Opportunity Radar (детерминирован) | systemd на живом сервере |
| дайджест, коды завершения, offset бота | перезапуск процессов в бою |

**Ни один веб-источник не включён.** Наличие класса адаптера и адреса в
`sources.yml` не делает источник рабочим: каждый адаптер нужно проверить
на живой странице отдельно. Адреса первоисточников из ТЗ (PSA OpenSTAT,
BOC issuances, Tariff Commission, BFAR, DTI Tradeline, DA, реестр
предприятий третьих стран ЕАЭС) внесены в конфигурацию выключенными,
с пометкой `verified: false`.

В выпуске три состояния источника различаются: «проверен», «ошибка
загрузки», «не подключён». При неполном покрытии пишется «часть источников
недоступна», а не «изменений нет». Фраза «подходящих закупок нет» не
появляется, если закупки не проверялись.

## Ключевые правила безопасности

* Публикация вывода возможна только после вердикта `PASS` рецензента
  (fail-closed). Недоступность модели никогда не даёт разрешение.
  Короткая фактическая новость может выйти без глубокого анализа, но тогда
  она помечается как непроверенная и не содержит рекомендаций.
* Проверка различает «по сообщению источника», «проверен первичный документ»
  и «требуется уточнение». PASS рецензента означает, что вывод согласован
  с материалом, а не что прочитан первичный документ.
* Подтверждённая доставка не повторяется. Если результат отправки неясен,
  доставка помечается неопределённой, и слепая повторная рассылка
  не выполняется: сообщение могло дойти.
* Профили компаний обновляются в режиме merge: пустое поле не затирает
  заполненное. Полная перезапись — только явным флагом.
* Telegram-бот отвечает только владельцу и только в личном чате.
* Telegram-аккаунт работает по белому списку методов чтения; авторизации
  и записи в коде нет.
* Текст источников считается недоверенным: он изолируется в промпте,
  инструкции внутри него исполнять запрещено, ответ модели валидируется.

## Границы системы

Система **не** делает и делать не должна:

* не отправляет письма и сообщения импортёрам и третьим лицам;
* не подаёт заявки на тендеры и не регистрирует компании;
* не публикует ничего в соцсетях;
* не действует от имени Telegram-аккаунта (только чтение);
* не утверждает, что компания допущена к поставкам — это проверяет человек.
