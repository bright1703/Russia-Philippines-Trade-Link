# PROCESS — рабочий процесс

## 1. Порядок запуска

Два автоматических прогона в неделю: понедельник и четверг, 08:00 по Маниле.
Ежедневного сбора и отдельных ежедневных уведомлений в проекте нет.

| Когда | Команда | Что делает |
|---|---|---|
| пн и чт, 08:00 Манила | `python -m trade_agent.run_pipeline --scheduled` | весь цикл: сбор → обработка → выпуск → доставка |
| постоянно | `python -m trade_agent.bot` | отвечает на команды владельца, сбор не запускает |

Плановый прогон сам проверяет, что за календарную неделю по Маниле выполнено
не больше двух автоматических циклов; догоняющий старт после простоя тоже
считается циклом. Одновременные прогоны исключены файловой блокировкой.

Этапы можно запускать и по отдельности — вручную, для проверки:

| Команда | Что делает |
|---|---|
| `python -m trade_agent.fetch` | обходит источники от их последних позиций |
| `python -m trade_agent.process` | Scout → Analyst → Reviewer → Radar |
| `python -m trade_agent.digest` | собирает выпуск и сохраняет его состав |
| `python -m trade_agent.notify` | доставляет последний собранный выпуск |

Тендерный модуль можно запускать и отдельно:
`cd tenders && python fetch_tenders.py`. Его собственный дайджест
(`tenders/latest.md`) продолжает работать независимо.

## 2. Какие источники проверяются

Список ведёт `sources.yml`. Включены по умолчанию: `tenders` (PhilGEPS, DA,
BFAR, DOE, NFA) и `telegram` (read-only). Веб-источники — DTI, DA, BAI, BFAR,
FPA, PSA, Tariff Commission, Bureau of Customs, ассоциации, пресс-релизы, СМИ —
описаны и выключены: их включают по одному, после проверки вёрстки.

## 2a. Как считается период сбора

Сбор продолжается от последней успешной позиции КАЖДОГО источника, а не
за фиксированные последние сутки.

| Ситуация | Что делает система |
|---|---|
| первый запуск источника | берёт предыдущие 7 дней |
| обычный запуск | интервал от последней позиции плюс перекрытие 12 часов |
| простой сервера | догружает весь пропущенный интервал, даже если он длиннее недели |
| очень долгий простой | догружает верхнюю границу (45 дней) и честно пишет, что остаток не покрыт |
| упёрлись в лимит канала | сохраняют курсор, период помечается как покрытый не полностью |

Между понедельником и четвергом непокрытого интервала не остаётся: окно
сбора всегда перекрывает разрыв между запусками.

## 3. Как определяется новый материал

Хэш содержимого: если у материала есть внешний идентификатор (номер закупки,
id сообщения) — он определяющий; иначе берётся нормализованный текст.
Повторный запуск того же сбора новых записей не создаёт.

Поверх этого работает ключ события (`trade_agent/events.py`): один факт,
перепечатанный двумя каналами, становится одной карточкой с несколькими
источниками. Ключ строится из значимых слов заголовка, даты и отрасли,
а при наличии ссылки на первичный документ — из неё. Два разных изменения
по одному товару по похожему заголовку НЕ объединяются.

## 4. Как отбрасывается шум

Порядок отсева, от дешёвого к дорогому:

1. слишком короткий материал;
2. стоп-слова (вакансии, поздравления, розыгрыши);
3. событие третьего рынка без связи с Филиппинами, РФ или маршрутом между
   ними — совпадения товара для включения недостаточно;
4. нет ни отраслевого слова, ни делового события в нашей юрисдикции;
5. для тендеров — отменена, просрочена или оценена тендерным модулем ниже порога;
6. оценка Scout ниже `SCOUT_MIN_SCORE`.

Пункты 1–5 работают без модели, поэтому недоступность LLM не мешает
отсеивать очевидный шум.

**Важное исключение.** Отсутствие товарного слова само по себе причиной
отказа не является. Бизнес-миссия, делегация, переговоры и выставка
российских компаний на Филиппинах проходят дальше и без товарного словаря:
именно на старом правиле «нет ни одного отраслевого ключевого слова»
терялись новости о выходе компаний на местный рынок.

## 5. Пороги

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `SCOUT_MIN_SCORE` | 2 | ниже — материал считается шумом |
| `ANALYST_MIN_SCORE` | 3 | с этого уровня запускается глубокий анализ |
| `REVIEWER_MAX_REVISIONS` | 2 | предел доработок, защита от цикла |
| `RADAR_MIN_MATCH_SCORE` | 2 | ниже — совпадение с компанией не сохраняется |
| `RADAR_MIN_SECTOR_SCORE` | 2 | порог отраслевой связи (она показывается отдельно от прямой) |
| `DIGEST_MIN_CONFIDENCE` | 0.4 | ниже — вывод не считается проверенным |
| `DIGEST_MAX_CARDS` | 8 | ориентир 5–8 содержательных карточек на выпуск |
| `DIGEST_LOOKBACK_DAYS` | 4 | период выпуска: интервал между двумя запусками в неделю |
| `FETCH_OVERLAP_HOURS` | 12 | перекрытие при догрузке: поздние публикации не теряются |
| `FETCH_MAX_BACKFILL_DAYS` | 45 | предохранитель догрузки после долгого простоя |

## 6. Как оценивается релевантность

Scout ставит 0–5: 5 — прямая возможность или прямое регуляторное изменение,
0 — не связано. Оценка и причина сохраняются в `signals`.

Opportunity Radar отдельно оценивает связь сигнала с каждой компанией
(0–5) по HS-кодам, товарной группе, категории, продукции и прямому упоминанию.

## 7. Как проверяются выводы (fail-closed)

Reviewer возвращает `PASS`, `REVISE`, `REJECT` или служебный `FAILED`.

**Правило:** публикация возможна только при `PASS`. Отсутствие подтверждения
никогда не превращается в разрешение.

| Что произошло | Вердикт | Статус сигнала | Что дальше |
|---|---|---|---|
| проверено, замечаний нет | PASS | `analyzed` | публикуется, создаются matches |
| есть исправимые замечания | REVISE | — | доработка Analyst, максимум `REVIEWER_MAX_REVISIONS` раз |
| выводы построены на выдумке | REJECT | `rejected` | закрыт |
| модель недоступна / пустой ответ / битый JSON | FAILED | `new`, счётчик попыток +1 | повтор в следующем запуске |
| попытки исчерпаны | FAILED | `failed` | ручной разбор |
| неизвестное значение verdict | FAILED | `failed` | ручной разбор, повтор бессмысленен |
| доработки исчерпаны без согласия | — | `needs_review` | ручной разбор |

Неподтверждённый сигнал **не создаёт matches** и **не попадает** в разделы
«Срочно», «Возможности», «Регуляторные изменения», «Тендеры» и «Наблюдать».
Он виден только в статистике раздела «Исключено», в `signals.last_error`
и в команде `/status`.

Даже при недоступности модели статические проверки продолжают работать,
но их результат не может дать PASS.

Разбор проблемных сигналов вручную:

```bash
sqlite3 data/trade_agent.db \
  "SELECT id, status, review_attempts, last_error, substr(reason,1,60) FROM signals
   WHERE status IN ('failed','needs_review') ORDER BY id DESC LIMIT 20;"
```

## 8. Что попадает в выпуск

| Раздел | Что внутри |
|---|---|
| Приморье → Филиппины | события, влияющие на поставки из Приморья на филиппинский рынок |
| Филиппины → РФ | филиппинский экспорт и условия ввоза в РФ |
| Что проверить или обсудить | не больше трёх обоснованных действий |
| Наблюдать | полезно знать, действия пока не требуется |

Срочные события выделяются ВНУТРИ этих разделов пометкой «СРОЧНО», отдельных
уведомлений вне расписания нет. Пустые разделы в выпуск не попадают. Один и
тот же сигнал не повторяется в двух разделах.

Состав выпуска формируется один раз и сохраняется в `issue_items`. Карточки,
счётчики шапки, список компаний и посты в Telegram строятся из этого набора,
поэтому шапка не может противоречить содержимому.

В карточке: понятный заголовок (не эмодзи), факт, значение для направления,
отрасль, компании с типом связи, дата, ссылка и уровень проверки. Внутренние
баллы Scout, сырые подсказки HS и причины модели в выпуск не выводятся —
они доступны в `/status`.

### Два вида связи с компаниями

| Вид связи | Что означает | Как показывается |
|---|---|---|
| Прямая применимость | в материале есть товар, подтверждённый код или название компании | компания, действие и фрагмент-основание |
| Отраслевая связь | событие в проверенной отрасли компании, применимость не установлена | «компании отрасли, применимость уточнить» |

В карточке — до трёх компаний и число остальных. Полный список доступен
командой `/companies <id>` с пагинацией, порядок воспроизводимый.

### Уровни проверки

| Пометка | Что значит |
|---|---|
| по сообщению источника | факт взят из пересказа, первичный документ не читали |
| проверен первичный документ | документ прочитан и подтверждает вывод |
| требуется уточнение | данных недостаточно, вывод не публикуется как проверенный |

## 9. Ограничения для иностранных компаний

Система никогда не утверждает, что компания вправе участвовать. Для тендеров
переносятся заметки о допуске из модуля `tenders`; Reviewer отдельно проверяет,
что ограничение «только для филиппинских поставщиков» не проигнорировано.
Финальная проверка — всегда у человека и у закупочной комиссии.

## 10. Какие файлы обновляются

* `data/trade_agent.db` — база (в Git не попадает);
* `digest/latest.md` и `digest/archive/YYYY-MM-DD.md`;
* `tenders/latest.md` и `tenders/archive/` — при отдельном запуске модуля;
* `logs/` — логи (в Git не попадают).

## 10a. Коды завершения

| Код | Когда | Что делать |
|---|---|---|
| 0 | всё отработало | ничего |
| 1 | частичный сбой: источник не ответил, есть отложенные или неподтверждённые элементы | посмотреть лог и `runs`; данные сохранены |
| 2 | критический сбой: этап не выполнен | разбираться немедленно |

`systemd` и `cron` видят ненулевой код. Код 1 не означает потерю данных.

## 10b. Профили компаний: источник правды

Источник правды — `brain/companies/*.md`. Синхронизация идёт в режиме merge:
**пустое поле профиля не затирает данные в базе**. Обычный запуск `process`
не может удалить товары, HS-коды и категории.

Полная перезапись — только явными флагами импорта:

```bash
python -m trade_agent.companies.import_companies catalog.csv              # merge
python -m trade_agent.companies.import_companies catalog.csv --overwrite  # полная замена
python -m trade_agent.companies.import_companies catalog.csv --write-profiles \
       --overwrite-profiles                                               # перезапись .md
```

## 11. Какие ошибки критические

Некритические — запуск продолжается, ошибка попадает в `runs` и в лог:
источник не ответил, robots.txt запрещает, вёрстка изменилась, PDF повреждён,
модель недоступна (материал остаётся в очереди), рецензия не состоялась
(сигнал не публикуется и ждёт повтора), одна запись не разобралась.

Критические — этап останавливается с ненулевым кодом:
нет или повреждён `sources.yml` / `profiles.yml`, база недоступна для записи,
каталог дайджеста не создаётся.

Признак скрытой поломки: ошибок нет, но `New raw items: 0` несколько дней
подряд — скорее всего изменилась вёрстка источника.

## 12. Проверка состояния

```bash
sqlite3 data/trade_agent.db "SELECT stage,status,processed,created,errors,started_at FROM runs ORDER BY id DESC LIMIT 10;"
```

или команда `/status` в Telegram-боте.

## 13. Как очищаются временные данные

`tenders/.raw/` очищается в конце каждого запуска тендерного модуля.
Логи ротируются автоматически (5 файлов по 2 МБ).
База растёт медленно; чистка старых `raw_items` пока делается вручную.

## 14. Git

Локальный коммит после изменений разрешён. `git push` выполняется
только по отдельному явному разрешению владельца.
